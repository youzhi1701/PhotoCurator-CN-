## 产品定位

PhotoCurator 的两个核心任务：

1. **模糊废片筛选**：快速找到明显模糊、失焦或质量不足的照片并人工复核。
2. **相似 / 重复照片筛选**：把连拍和高度相似照片归组，快速删除不需要的版本。

评分 / 精选推荐不再参与默认清理主流程，作为工具箱扩展功能保留。

图片扫描不再只依赖固定短名单：运行时会自动纳入当前 Pillow 实际可解码的全部扩展格式，并在可用时加入 HEIC/HEIF/HIF 与 RAW（CR2/CR3/NEF/ARW/DNG/RAF/ORF/RW2/PEF 等）支持。

## v1.7.4 运行与界面架构

### 前台优先

前台负责：
- 照片展示与大图预览
- 用户筛选决策
- 即时状态反馈
- 当前工作区的局部更新

耗时文件操作不会再阻塞筛图界面。

### 后台任务中心

后台负责：
- 移入软件回收站
- 恢复与永久删除
- 数据库、索引与操作日志
- 清晰度分析
- 相似特征分析
- 缩略图与缓存维护

重要文件任务通过持久化任务队列执行，具有任务状态、优先级、幂等保护和异常恢复能力。程序异常退出后，未完成的重要任务可重新进入队列。

文件移动类任务还会在入队时提前持久化目标路径。即使程序恰好在“文件已经移动、数据库状态尚未提交”的瞬间被强制结束，下次启动也可以根据任务记录继续完成回收站索引、恢复状态与生命周期同步，而不是丢失文件去向。

### 双核心并行

默认“开始分析”同时启动：
- 模糊 / 清晰度分析
- 相似 / 重复照片分析

两条核心分析可以并行运行，用户不必先完成一整轮模糊筛选再开始重复照片筛选。前台在后台运行期间保持可操作。

两条分析共享同一轮目录枚举快照：超大图库由单一生产者完成遍历，其它分析等待并复用结果，不会因为固定超时重新扫一遍机械硬盘。Cull 与 Dedup 无论谁先完成，最终都会经过资格同步屏障，保证后来判定为模糊的照片不会继续作为相似组有效保留项。HTTP 启动入口也使用原子门禁，避免多线程请求重复启动同一步骤。

### 稳定前台结果

后台分析结果不会再以“每分析一张就重绘一次页面”的方式干扰当前工作区：
- 当前视图保持稳定
- 后台结果先缓存
- 用户按需加载最新结果
- 相似组按状态分区、分块载入
- 大图库限制单次前台渲染量

## 核心工作区

### 模糊废片

- 清晰 / 轻微软 / 模糊三级结果
- 用户决策高于算法建议
- 点击照片打开大图
- 删除默认进入 PhotoCurator 软件回收站
- 批量处理也进入后台任务队列
- 扫描 / 分析时仍可继续复核已有结果

### 相似照片

相似组具有持久化生命周期：
- **待筛选**
- **已筛选**
- **已筛选 · 有新增**

已经筛选过的组不会重新混回“待筛选”。

如果后来在其它文件夹扫描到新的相似成员，原组会保留历史决策并进入“有新增”状态，不会静默覆盖原结果。

照片生命周期也独立持久化：
- 正常
- 待移入回收站
- 已移入回收站
- 待恢复
- 已永久删除

已移入软件回收站的成员仍可在原相似组中保留历史关系，用于复核和恢复。

### 软件回收站

所有普通“删除”默认进入：

`PhotoCurator_RecycleBin（软件回收站）`

支持：
- 单张 / 批量恢复
- 单张永久删除
- 清空软件回收站
- 缩略图和大图最终复核

删除确认弹窗中：
- **Enter**：移入软件回收站
- **P**：彻底删除
- **Esc**：取消

软件回收站目录自动排除在后续扫描之外。

每个图库的软件回收站还保存 `.photocurator-trash.json` 恢复清单，使原路径信息不只依赖安装目录中的数据库；重装或清理程序配置后仍具备恢复元数据。

## 界面与布局

v1.5.0 的布局原则：

- **照片工作区最大化**
- 主流程、设置、后台任务、工具箱职责分离
- 左侧导航可折叠
- 照片来源、筛选设置、统计信息可折叠

## 本地数据结构

核心数据继续使用本地 SQLite，并按职责划分：

- 分析缓存：清晰度、评分、相似特征等可重建数据
- 用户决策：照片生命周期与人工状态
- 相似组：稳定组身份、组状态与历史成员
- 后台任务：queued / running / done / failed
- 操作日志：关键用户操作和后台处理记录
- 软件回收站：中央索引 + 图库内独立恢复清单

原则：**算法结果可以重算，用户决策不能被重算覆盖。**

## 构建、发布与版本机制

GitHub Actions：
- `.github/workflows/syntax-check.yml`
- `.github/workflows/build-release.yml`

普通 `main` 推送只运行源码/结构门禁，不会反复消耗 Windows 正式安装包构建；Windows Candidate 通过 Pull Request 或手动触发完成真实 EXE、窗口存活和测试安装包验证。正式 Release 仅由显式发布请求或匹配版本标签触发。

发布目标由 `packaging/release_manifest.json` 驱动。当前目标为 **1.7.4 Candidate**；只有全部 Release Gate 通过后，才允许创建正式标签：

`v1.7.4`

发布工作流接受 `v*` 标签，但会在构建开始时强制检查：**Git 标签必须与 manifest 中的版本完全一致**。标签不一致会直接失败，避免误把旧代码发布成新版本或把新代码挂到旧标签。

当前 Candidate 安装包目标名称：

`PhotoCurator-Setup-v1.7.4.exe`

当前已经公开可下载的 Stable 安装包仍为 **v1.5.0**。

CI 同时校验以下版本必须一致：
- `desktop_app.py` / `photo_curator.py` 的应用版本
- `packaging/release_manifest.json`
- Inno Setup 默认版本
- Windows EXE VersionInfo
- 安装包命名规则

因此后续升级版本时，不再需要在 Release 工作流中复制修改多个硬编码标签；工作流从 manifest 动态得到版本、安装包名和正式 Release 标签。

## 更新与兼容

PhotoCurator 使用固定 AppId 原位覆盖升级。正式安装与运行数据分离：

```text
%LOCALAPPDATA%/Programs/PhotoCurator/
└─ app/                         # 可替换程序文件

%LOCALAPPDATA%/PhotoCurator/
└─ data/                        # 持久化配置、数据库、缓存、日志、测试数据
```

正式 EXE 位于安装目录的 `app/PhotoCurator.exe`，运行数据固定写入 `%LOCALAPPDATA%/PhotoCurator/data`。即使以后把程序安装到其它磁盘或受保护目录，也不会改变用户数据位置。覆盖升级只清理并替换程序 `app/`，不会把运行数据混进程序替换目录。

从旧版 `{app}/data` 升级时，自 v1.6.0 建立的数据迁移机制会在首次启动时自动迁移并合并历史 `config` 持久化状态（SQLite 索引、人工筛选决策、相似组状态、后台任务、最近目录和相似特征存储）。缓存、日志和内置测试数据属于可重建数据，不作为迁移阻塞条件；若迁移异常，桌面壳会继续使用旧数据目录并写入迁移告警，避免出现“升级后像丢数据”的空白状态。

升级原则：
- 只替换程序文件
- 保留设置
- 保留本地索引和分析缓存
- 保留操作日志
- 保留后台任务数据库
- 保留用户照片
- 保留 PhotoCurator 软件回收站
- 保留图库内恢复清单
- 不因程序升级覆盖或删除用户原照片

显式退出时会先请求正在运行的分析线程停止。若仍有后台文件任务，界面会提示其数量；这些任务已持久化，退出后未完成部分会在下一次启动继续恢复执行。

## 长期维护分层

后续修改按职责定位，不再把状态、文件操作和界面逻辑混在一起：

- **核心分析层**：Cull / Dedup / Rank 的算法与分析线程。Cull + Dedup 是默认双核心；Rank 保持工具箱扩展。
- **扫描与缓存层**：统一图库枚举、共享扫描快照、清晰度缓存、相似特征缓存、缩略图缓存。缓存属于可重建数据，不承载用户决策。
- **用户状态层**：人工分类、相似组选优、组生命周期、媒体生命周期。这里的数据优先级高于算法重算。
- **文件生命周期层**：软件回收站、恢复、永久删除、路径迁移。所有危险文件操作通过持久化任务与幂等恢复机制执行。
- **后台任务层**：`background_tasks.py` 只负责队列、优先级、恢复、状态与执行调度，不承载 UI 业务规则。
- **API / 状态协调层**：`photo_curator.py` 负责启动门禁、跨阶段同步、状态快照和前端接口；并行任务的完成顺序必须通过统一同步屏障收口。
- **桌面壳层**：`desktop_app.py` 负责窗口、托盘、单实例、本地服务生命周期和显式退出，不直接实现照片业务；`runtime_paths.py` 统一运行数据目录和旧版数据迁移策略。
- **发布与兼容层**：`packaging/` + GitHub Actions 负责版本、安装布局、覆盖升级和发布门禁。用户数据目录与程序替换目录必须长期隔离。
- **日志与诊断层**：运行日志、任务状态、操作日志用于定位问题；不以吞掉异常或静默修复代替真正的状态一致性。

维护原则仍是：成熟模块不为“看起来更整洁”而重写；只有稳定性、数据一致性、性能、可维护性或扩展性存在实际问题时才调整公共机制。

## 安全边界

默认原则：**先分析、再审核、普通删除可恢复，永久删除必须明确确认。**

- 普通删除不进入 Windows 回收站，而进入 PhotoCurator 软件回收站
- 永久删除是独立危险操作
- 恢复时不覆盖已有同名文件
- 软件生成目录不会重新进入扫描
- 照片分析、缩略图、RAW / HEIC 解码在本机执行
- GPS 地图功能如启用，可能向地图 / 地理编码服务发送经纬度，但不会上传照片文件

## v1.7.4 Stable 发布门槛

正式发布前必须同时满足：
- Python / 嵌入式 JavaScript / HTML / CSS 自动检查通过
- Windows Candidate 从源码测试一路通过到打包 EXE、原生窗口响应性、测试 Installer 与 artifact
- Catalog 完整扫描只有在零 I/O 错误时才允许执行“未见到 → missing”；中断或 partial 扫描不得误判缺失
- SQLite 数据库迁移前有可验证备份，运行时连接不会在 Windows 残留文件锁
- 设备拔插、盘符变化、离线图库和 Preview Store 不破坏稳定 media identity
- 模糊和相似两条核心分析可并行，人工复核状态不会串组或被后台结果覆盖
- 后台文件任务不阻塞前台筛选
- 软件回收站删除 / 恢复 / 永久删除 / 跨盘移动链路一致，异常中断可恢复
- 相似组历史状态和新增成员逻辑正确
- 支持格式必须给出明确处理结果，Pillow fallback、RAW / HEIF 与 sidecar 路径可回归验证
- 大图库使用分页 / 虚拟化 / 增量机制，不因几十万媒体一次性渲染拖死 UI
- 内置测试数据可正常使用
- Windows 托盘和正式图标随安装包可用
- 安装包自检、SHA256 与发布后 Release asset 验证通过
- 正式程序目录与运行数据目录完全分离
- 旧版安装目录数据可安全迁移或异常回退
- 覆盖升级不破坏用户数据库、索引、设置、日志、任务状态和用户照片
- GitHub Release 中真实存在与版本一致、非空且校验通过的 Windows 安装包

在上述门槛没有全部满足前，v1.7.4 只能保持 **Candidate**，不能标记为 Stable。
